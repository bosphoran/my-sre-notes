## Introduction

In K8s, authentication checks the identity of a user, service account, or API client.

Methods include:

- Certificates (client TLS certs)
- Bearer tokens (ServiceAccount tokens, OIDC tokens)
- Authentication plugins (LDAP, cloud IAM, etc.)

Once authenticated, K8s checks if you’re allowed to perform the requested action.

- **Role-Based Access Control (RBAC):** RBAC regulates access based on user or group roles. It assigns permissions to roles. Users or groups are then assigned to these roles.
- **Attribute-Based Access Control (ABAC):** ABAC defines policies based on API request attributes. These attributes can include user roles, resource names, or namespaces. ABAC is used for complex and granular access control. 
- **Node Authorization:** This is a specific security mechanism. It controls API requests made by kubelets. Kubelets are agents that run on each node. They manage pods and containers.

> **Authentication** = identity check (who are you?). **Authorization** = permission check (are you allowed to do this?)

### Authentication Methods

We will look at two key authentication methods.

1. **X.509 Certificates**

A classic example of **X.509 Certificates** based authentication is the **Kubeconfig** file we use to connect to the cluster. If you open the Kubeconfig file you will find the client certificate data in **base64** encoded format.

```bash
vagrant@controlplane:~$ grep -A 1 'client-certificate-data' ~/.kube/config
    client-certificate-data: LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0tCk1JSURLVENDQWhHZ0F3SUJBZ0lJYitkd
```

![RBAC]({{ site.baseurl }}/assets/img/k8s-course/rbac.jpg)

Here is how the certificate-based authentication works.

   1. The user (developer) executes a kubectl command on their workstation.
   2. The kubectl command reads the kubeconfig file located at $HOME/.kube/config.
   3. The kubeconfig file contains the client certificate and key data (base64-encoded) needed for authentication.
   4. The kubectl request, along with the client certificate, is sent to the Kubernetes API server over a TLS handshake.
      - The API server verifies if the client certificate is signed by the trusted cluster Certificate Authority (CA). If the certificate is valid, the request is authenticated, and it is forwarded for authorization.
      - If the certificate is invalid, the TLS handshake is aborted, and the request is rejected.

2. **Bearer Tokens**

General Meaning: A bearer token is a security token that grants access to protected resources to anyone who possesses it, without requiring additional authentication.

Applications running inside the pod make use of this token to access the API server resources.

![RBAC 2]({{ site.baseurl }}/assets/img/k8s-course/rbac-2.jpg)

### Authorization Methods

The authorization modes are specified using the **--authorization-mode** flag in the **kube-apiserver** command.

One way to check the authorization modes is by describing the **kube-apiserver-controlplane** pod in the **kube-system** namespace and filtering the output to display only the relevant authorization settings.

```bash
vagrant@controlplane:~$ kubectl describe po kube-apiserver-controlplane -n kube-system | grep authorization
      --authorization-mode=Node,RBAC
```

The output shows that the K8s cluster is configured with two authorization modes: **Node** and **RBAC**.

### Need for Role Based Access Control

In an organization, there are various user groups with different responsibilities and access requirements. For example:

- Developers: Responsible for building and maintaining applications.
- DevOps Engineers: Manage the infrastructure and deployment processes.
- Support Teams (L1, L2, etc.): Handle support and troubleshooting.

In addition to user groups, K8s also utilizes service accounts to represent non-human entities, such as applications, **CI/CD tools**, and **monitoring tools** that interact with the cluster.

---

### RBAC Concepts

RBAC centers on three key elements:

1. **Subjects:** Refer to entities that interact with the cluster and request actions on its resources. These subjects can be users, groups, or service accounts
2. **Actions:** Refer to operations that subjects (users, groups, or service accounts) can perform on K8s resources (pods, deployments, services etc). These actions are defined by verbs (get, list, create, update, patch etc).
3. **Objects:** Can be any K8s resource for which access is required. For example, pods, deployment, PV, PVC, configMaps, Secret, etc. A subject can perform actions on objects.

### Create a User

The current user we are using to access the cluster using **kubectl** is the **admin user** that has all the permissions to the cluster.

We will create a custom user (sre) with Certification-based authentication.

Here is a high-level workflow for creating a user based on certificate-based authentication.

![RBAC 3]({{ site.baseurl }}/assets/img/k8s-course/rbac-3.jpg)

Perform all the following steps from the control plane node.

**Step 1:** Create a private key and certificate signing request (CSR) for the user.

When a user wants to authenticate to the K8s cluster using a client certificate, they first generate a private key and a CSR. The CSR contains the user's public key and other metadata, such as the username and groups the user belongs to.

Create a folder named **sre-user** and change it into the directory. Perform all the steps from this folder.

```bash
vagrant@controlplane:~$ mkdir sre-user && cd sre-user
vagrant@controlplane:~/sre-user$

# Use the following commands to create the public key and CSR.
vagrant@controlplane:~/sre-user$ openssl genrsa -out sre.key 2048
# 
vagrant@controlplane:~/sre-user$ openssl req -new -key sre.key -out sre.csr -subj "/CN=sre/O=devops"
```

**Step 2:** Submit CSR to K8s

Now we need to create a **CertificateSigningRequest** (CSR) resource in K8s by submitting the CSR data.

**CertificateSigningRequest** is a K8s resource that represents a request to the K8s API server to sign a client certificate. It is used as part of the process to generate and approve client certificates for user authentication in K8s.

```bash
# Create CertificateSigningRequest for SRE user.
vagrant@controlplane:~/sre-user$ cat << EOF | kubectl apply -f -
apiVersion: certificates.k8s.io/v1
kind: CertificateSigningRequest
metadata:
  name: sre-csr
spec:
  request: $(cat sre.csr | base64 | tr -d '\n')
  signerName: kubernetes.io/kube-apiserver-client
  usages:
  - client auth
EOF
certificatesigningrequest.certificates.k8s.io/sre-csr created
```

**Step 3:** Approve the CSR

As a K8s administrator, you can verify the **CertificateSigningRequest**.

```bash
vagrant@controlplane:~/sre-user$ kubectl get csr
NAME      AGE   SIGNERNAME                            REQUESTOR          REQUESTEDDURATION   CONDITION
sre-csr   79s   kubernetes.io/kube-apiserver-client   kubernetes-admin   <none>              Pending
```

Now, approve the **CertificateSigningRequest**. Usually, this process is handled by the cluster administrators.

```bash
vagrant@controlplane:~/sre-user$ kubectl certificate approve sre-csr
certificatesigningrequest.certificates.k8s.io/sre-csr approved
```

Once the CSR is approved, the K8s API server signs the CSR using its private key.

**Step 4:** Get the Signed Certificate

The **sre** user can now use the signed certificate along with their private key to authenticate to the K8s cluster.

```bash
# To get the signed certificate, execute the following command.
vagrant@controlplane:~/sre-user$ kubectl get csr sre-csr -o jsonpath='{.status.certificate}' | base64 -d > sre.crt
```

**Step 5:** Create a Kubeconfig file for the user

Now that we have all the required certificates, we can create a Kubeconfig file for the user **sre** to authenticate with the cluster.

```bash
# Create a new Kubeconfig file named sre-config for the user SRE.
vagrant@controlplane:~/sre-user$ touch sre-config
```

Save the following as **config.sh**. This script generates all the required configurations in sre-config using kubectl config.

```bash
#!/bin/bash

# Set the desired kubeconfig file name
KUBECONFIG_FILE="sre-config"

# Get the cluster name
CLUSTER_NAME=$(kubectl config current-context)

# Get the cluster endpoint
CLUSTER_ENDPOINT=$(kubectl config view -o jsonpath='{.clusters[*].cluster.server}')

# Set the user credentials
kubectl config --kubeconfig=$KUBECONFIG_FILE set-credentials sre --client-key sre.key --client-certificate sre.crt --embed-certs=true

# Set the context
kubectl config --kubeconfig=$KUBECONFIG_FILE set-context sre --cluster $CLUSTER_NAME --user sre

# Set the cluster information
kubectl config --kubeconfig=$KUBECONFIG_FILE set-cluster $CLUSTER_NAME --server=$CLUSTER_ENDPOINT

# Get the base64-encoded CA certificate
CA_CERT_DATA=$(cat /etc/kubernetes/pki/ca.crt | base64 | tr -d '\n')

# Set the CA certificate in the kubeconfig file
kubectl config --kubeconfig=$KUBECONFIG_FILE set clusters.$CLUSTER_NAME.certificate-authority-data $CA_CERT_DATA

# Set the current context to "sre"
kubectl config --kubeconfig=$KUBECONFIG_FILE  use-context sre
```

Change the permissions and execute the script.

```bash
vagrant@controlplane:~/sre-user$ chmod +x config.sh && ./config.sh
User "sre" set.
Context "sre" created.
Cluster "kubernetes-admin@kubernetes" set.
Property "clusters.kubernetes-admin@kubernetes.certificate-authority-data" set.
Switched to context "sre".
```

You can view the config using,

```bash
vagrant@controlplane:~/sre-user$ kubectl --kubeconfig=sre-config config view
apiVersion: v1
clusters:
- cluster:
    certificate-authority-data: DATA+OMITTED
    server: https://192.168.201.10:6443
  name: kubernetes-admin@kubernetes
contexts:
- context:
    cluster: kubernetes-admin@kubernetes
    user: sre
  name: sre
current-context: sre
kind: Config
users:
- name: sre
  user:
    client-certificate-data: DATA+OMITTED
    client-key-data: DATA+OMITTED
```

If you open the **sre-config** file, you can view all the configurations needed to connect to the cluster.

**Step 6:** Validate the sre-config file

By default, kubectl is configured with the admin config file located at **$HOME/.kube/config**.

We can override this behavior by explicitly specifying a kubeconfig file using the **--kubeconfig** parameter. In our case, it's **sre-config**.

Let's check if the **sre user** can list pods in the cluster.

```bash
vagrant@controlplane:~/sre-user$ kubectl --kubeconfig=sre-config get pods
Error from server (Forbidden): pods is forbidden: User "sre" cannot list resource "pods" in API group "" in the namespace "default"
```

As you can see from the output, the **user SRE** is successfully authenticated but does not have the necessary authorization to list pods in the default namespace.

To resolve this issue, you need to ensure that the **user SRE** has the appropriate permissions to list pods in the namespace. This is typically done through **Roles and ClusterRoles**.

### RBAC in Real World Projects

In real-world project environments, users and groups are not managed manually. This task is typically handled by centralized identity providers.

Organizations use centralized identity providers and integrate them with various applications and services for the following reasons.

- Single Sign-On (SSO)
- Centralized User Management
- Multi-factor authentication (MFA) and other security features
- Compliance and Governance

**Third-Party Identity Providers:**
K8s supports integration with external identity providers like Active Directory, LDAP, or OAuth providers (e.g., Google, Okta, etc.).

**Cloud Provider Integration:**
When running managed Kubernetes clusters on cloud platforms like AWS, GCP, or Azure, you can leverage the cloud provider's identity and access management (IAM) services.
