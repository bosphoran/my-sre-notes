## Introduction

Consider a scenario where you need to expose multiple endpoints outside the cluster, say ten different applications. This would require creating ten separate LoadBalancers.

![Ingress]({{ site.baseurl }}/assets/img/k8s-course/ingress.jpg)

While this approach might seem simple, it is not efficient and can quickly become costly, as running multiple LoadBalancers incurs significant expenses.

### Implementing a Reverse Proxy

Instead of deploying multiple LoadBalancers, a more efficient approach is to deploy an NGINX **reverse proxy** and expose that as a single LoadBalancer.

![Ingress 2]({{ site.baseurl }}/assets/img/k8s-course/ingress-2.jpg)

Within the NGINX configuration, you can define routing rules that direct traffic to each of the ten applications. This way, you reduce the number of LoadBalancers needed, optimizing both resource usage and cost.

However, there are some challenges with this setup, as outlined below.

1. **Configuration Management:** You will need to manage the routing rules within the NGINX configuration, typically using a ConfigMap in K8s. This adds complexity, as any changes to the routing rules require Nginx pod needs to be reloaded or re-deployed.
2. **DNS Updates and Rollouts:** When new DNS information needs to be added, you will have to roll out changes to the NGINX deployment, which can be time-consuming and troublesome.
3. **Dynamic Service Discovery:** To avoid frequent rollouts, you may need to implement a custom service discovery solution, such as Consul, which dynamically updates the routing rules in the NGINX configuration. This adds another layer of complexity but can significantly streamline the process of managing and updating endpoints.

> K8s **ingress** solves all these issues and makes exposing applications outside the cluster simpler.

K8s **Ingress** is a resource to add rules to route traffic from external sources to the applications running in the K8s cluster.

### Ingress

**Ingress** refers to traffic entering the cluster, while egress refers to traffic exiting the cluster.

![Ingress 3]({{ site.baseurl }}/assets/img/k8s-course/ingress-3.jpg)

### What is Kubernetes Ingress?

**Ingress** is used for managing external access to services within a K8s cluster. Ingress is namespace-scoped.

It acts as a single entry point for incoming HTTP and HTTPS traffic, allowing you to define routing rules that direct this traffic to the appropriate backend services based on hostnames and paths.

To understand ingress better, you need to be clear about two key concepts:

1. K8s Ingress Resource
2. K8s Ingress Controller

### Ingress Resource

Ingress is a native K8s resource, just like pods and deployments. With an Ingress object, you can manage DNS routing configurations, allowing you to direct external DNS requests to specific services within the cluster.

![Ingress 4]({{ site.baseurl }}/assets/img/k8s-course/ingress-4.png)

The above **Ingress object** means that all requests to **api.techiescamp.com** should be directed to the service named **api-service** in the backend namespace.

> Essentially, **ingress** sets the routing rules for incoming traffic. Which means, when we create a Ingress object we are just creating the routing rules.

When a DNS request is made, such as for api.techiescamp.com, where does the traffic first enter the K8s cluster?

This is where the **Ingress controller** comes in to picture.

### Ingress Controller

**Ingress Controller** manages the routing of external traffic to the correct services based on the Ingress rules.

The **ingress controller** is not a native K8s implementation. We need to set up an ingress controller for the ingress rules to function.

An **Ingress controller** typically functions as a **reverse proxy server** within the cluster. In K8s, it is deployed as a Deployment and exposed via a Service of type LoadBalancer. This allows it to manage and route external traffic to internal services.

> **Ingress controller** handles incoming HTTP/HTTPS requests from the loadbalancer and routes them to the appropriate service inside the cluster, based on path-based (e.g., /api, /web) or host-based (DNS) routing rules.

![Ingress 5]({{ site.baseurl }}/assets/img/k8s-course/ingress-5.jpg)

1. The K8s **Ingress object** defines routing rules for incoming HTTP(S) traffic to services within the cluster. These rules are stored within the cluster as K8s objects (etcd)
2. K8s **ingress controllers** (Nginx/HAProxy etc.) reads these rules and handles the actual routing of traffic according to the DNS rules specified in the Ingress resource.

### Role of Load Balancer

For the traffic to enter the cluster, we need a Load Balancer to distribute the incoming traffic to ingress controller service. The Load Balancer is typically created by the Ingress Controller service, using the type LoadBalancer.

Once traffic reaches the Ingress Controller pods, routing decisions, meaning which backend service the traffic should be sent to, are made based on the rules defined in the Ingress object.

### Cross Namespace Routing

If you need to route traffic to a service in a different namespace, you can use an **ExternalName service**.

### Ingress Controller: Internal Workflow

Let’s take an example of an **Nginx ingress controller** implementation to understand how it works.

In Nginx, the routing rules are usually defined in the **nginx.conf** file. The rules we create using the ingress object should be reflected in the nginx.conf file for Nginx to route traffic to the correct service backend.

> The **NGINX Ingress controller** translates the routing rules (such as host-based or path-based routing) into NGINX configuration files. These configurations specify how incoming traffic should be forwarded to the appropriate backend services (pods) within the Kubernetes cluster.

### Admission Controller & Validating Webhook

K8s **Admission Controller** is a small piece of code that intercepts and validates or mutates K8s objects before they are persisted in the cluster.

Without an **admission controller**, you might deploy an ingress object with **incorrect configurations**.

The **misconfigurations** handled by the admission controller refer to the values used in certain parameters (e.g., incorrect hosts or invalid annotations).

### Ingress Object

To understand the **ingress object** better, lets take an example of an e-commerce website that has the following hostnames.

- **shop.techiescamp.com:** Used by end users to browse and shop on the website.
- **api.techiescamp.com:** Used by third-party applications to interact with the e-commerce platform via API endpoints.

As you may know, every e-commerce website has multiple URL subpaths for both web and API endpoints. For example, think of popular e-commerce platforms like Amazon or Flipkart.

**For shop.techiescamp.com:**

- https://shop.techiescamp.com/shop : Main shopping page.
- http://shop.techiescamp.com/shop/products: Displays product listings.
- https://shop.techiescamp.com/v2/search: Endpoint for product searches.
- https://shop.techiescamp.com/v2/search?query=iphone: Example of a product search query URL (searching for "iPhone")

**For api.techiescamp.com:**

- https://api.techiescamp.com/v2/products: Fetches the list of products.
- https://api.techiescamp.com/v2/products/456: Retrieves details for an individual product (product ID 456).

The following Ingress Object implements all the mentioned hostnames and URL subpaths, routing them to their respective services running inside the cluster.

```bash
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: techiescamp-ingress                # Name of the Ingress resource
  namespace: default                       # Namespace where this Ingress resides
  annotations:
    nginx.ingress.kubernetes.io/ssl-redirect: "true"   # Forces HTTPS redirection
    nginx.ingress.kubernetes.io/rewrite-target: /      # Rewrites incoming request paths to "/"
spec:
  ingressClassName: nginx                  # Specifies which Ingress controller to use (nginx)
  tls:
  - hosts:
      - shop.techiescamp.com               # TLS enabled for shop domain
    secretName: shop-techiescamp-tls-secret # Secret containing TLS cert/key for shop domain
  - hosts:
      - api.techiescamp.com                # TLS enabled for api domain
    secretName: api-techiescamp-tls-secret  # Secret containing TLS cert/key for api domain

  rules:
  - host: shop.techiescamp.com             # Routing rules for shop domain
    http:
      paths:
      - path: /shop                        # Requests to /shop go to shop-main-service
        pathType: Prefix
        backend:
          service:
            name: shop-main-service
            port:
              number: 80
      - path: /shop/products               # Requests to /shop/products go to shop-product-service
        pathType: Prefix
        backend:
          service:
            name: shop-product-service
            port:
              number: 80
      - path: /shop/search                 # Requests to /shop/search go to shop-search-service
        pathType: Prefix
        backend:
          service:
            name: shop-search-service
            port:
              number: 80
              
  - host: api.techiescamp.com              # Routing rules for api domain
    http:
      paths:
      - path: /v2/products                 # Requests to /v2/products go to api-product-service
        pathType: Prefix
        backend:
          service:
            name: api-product-service
            port:
              number: 80
      - path: /v2/products/456             # Requests to /v2/products/456 go to api-product-service
        pathType: Prefix
        backend:
          service:
            name: api-product-service
            port:
              number: 80
```

It’s important to understand the Prefix path type. The Prefix ensures that any request with a URL path starting with the specified string will match and be routed to the appropriate backend service.

In an e-commerce website, when you search for a product, like "iPhone," a dynamic query string URL is generated. For instance, **shop.techiescamp.com/shop/search?query=iphone**.

Since every search generates a unique URL, it’s impractical to add every possible URL to the Ingress routing.

By using the Prefix path **/shop/search**, which directs traffic to the **shop-search-service**, any query or parameter added after this path will be sent to the search service.

The backend application will handle processing the search request and generating the appropriate response, meaning it is part of the application's functionality.

The Ingress only handles routing the request to the appropriate service based on the path, while the application itself manages the logic behind processing dynamic parameters, like search queries, and responding to the user.

When multiple paths match a request, the Ingress controller uses the longest path match principle to decide which backend service to route the traffic to.

### Ingress Demo Application Architecture

Let’s say you’re building an e-commerce platform with three main services:

- Frontend App: This is the public website where users browse products and make purchases.
- API Service: It handles data communication between the frontend and backend.
- Payment Service: This service manages transactions and payments.

Now, we need to make the Frontend App available to the public so users can access the website, browse products, and place orders.

In this case, we’ll also expose the API and Payment Services to allow other business applications (not directly users) to connect to them. These might be partner apps or third-party tools that need to communicate with our platform.

To understand the **host-based** and **path-based routing** features of Ingress, let’s explore the following scenarios:

🖥️ **Frontend App**

- shop.techiescamp.com: Routes traffic to the Frontend App, allowing users to browse products and access the main website.
- shop.techiescamp.com/cart: Routes traffic to the Frontend App to display items users have added to their cart.
- shop.techiescamp.com/orders: Routes traffic to the Frontend App to list users' previous orders.

⚙️ **API Service**

- shop.techiescamp.com/api: Routes traffic to the API Service to handle backend operations, such as order management and product updates.
- shop.techiescamp.com/api/inventory: Specifically routes traffic to the Inventory API (a part of the API Service) to manage stock levels and check product availability.

💳 **Payment Service**

- shop.techiescamp.com/payment: Routes traffic to the Payment Service to securely process user transactions.

### Ingress TLS

When working with Ingress in production, most implementations use TLS certificates for the DNS hostnames.

> **TLS termination** refers to the process of decrypting incoming encrypted traffic at a certain point in the network, typically at the load balancer or proxy layer, before it reaches the backend servers (like application servers or pods in K8s).

When you add TLS to an Ingress, the TLS termination happens at the Ingress layer.

This means that encrypted traffic reaches the Ingress controller, but from the Ingress controller to the pod, the traffic is not encrypted (non-SSL).

![Ingress 9]({{ site.baseurl }}/assets/img/k8s-course/ingress-9.jpg)

### Full SSL (End-to-End Encryption) to the Pod

Some industries, like finance and healthcare, have strict regulations requiring encryption throughout the entire communication path from the client to the backend.

To achieve this, you need to configure end-to-end encryption (full SSL) in K8s, meaning the traffic stays encrypted from the client, through the Ingress controller, all the way to the backend pod.

To enable full SSL, the backend service (your pod) must be configured to handle TLS traffic. This involves:

- Mounting a valid TLS certificate and private key on the pod, which the application server will use to serve SSL traffic.
- Configuring the application within the pod to listen for HTTPS requests, typically on port 443.

Which means there would be two different TLS certificates:

1. One at the Ingress level.
2. One for the application running in the pod.

![Ingress 10]({{ site.baseurl }}/assets/img/k8s-course/ingress-10.jpg)

### How Does Ingress TLS/SSL Work?

SSL is handled by the Ingress controller, not the Ingress resource itself. When you add SSL certificate to the Ingress resource as a K8s secret, the Ingress controller accesses those certificates and adds it to its configuration.
