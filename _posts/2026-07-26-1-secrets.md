## Introduction

A K8s **Secret** is an object used to store sensitive information such as passwords, API keys, tokens, or certificates. Unlike ConfigMaps (which hold non-sensitive configuration), Secrets are designed to keep data secure and avoid exposing it directly in Pod specs or application code.

```bash
# Secret file in plain text befor creation
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:                # Plain text values (Kubernetes will encode them automatically)
  username: admin
  password: mypassword123

# Once created, it is converted to bas64 format
apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
data:                      # Values must be base64 encoded
  username: YWRtaW4=        # "admin" in base64
  password: bXlwYXNzd29yZDEyMw==  # "mypassword123" in base64
```

### Secret Types

We use secrets for various purposes.

- We might need to store a TLS certificate to configure TLS for applications.
- We might need to store an API token for applications to use as a property for connecting to a different service.
- We might need to store a Kubernetes service account token for pods to authenticate to the API server.
- Or you might want to store an SSH key for SSH authentication.

Following are the built-in secret types available in Kubernetes.

- Opaque: Arbitrary user-defined data. For example, API keys, passwords, etc
- kubernetes.io/service-account-token: Tokens for Kubernetes service accounts to authenticate with the Kubernetes API server.
- kubernetes.io/dockercfg (legacy format): Docker registry credentials to pull private images that require authentication.
- kubernetes.io/dockerconfigjson: Recommended secret type to store docker registry credentials.
- kubernetes.io/basic-auth: Username and password for basic authentication
- kubernetes.io/ssh-auth: SSH private keys for accessing servers or repositories.
- kubernetes.io/tls: TLS Certificates and private keys for HTTPS connections.
- bootstrap.kubernetes.io/token: Tokens used for securely bootstrapping new nodes into a Kubernetes cluster.

### Working With Secrets

K8s automatically converts the plain text to **base64** encoded data when you create the secret.

```bash
# Create app-secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: app-secret
stringData:
  api_key: asdfw435sef2345
  db.properties: |
    username: dbuser
    password: dbpassword
type: Opaque
```

We use the **stringData** field to include human-readable secret data, which makes the secret YAML file more convenient to read and manage.

```bash
# Let's create the secret.
vagrant@controlplane:~$ kubectl apply -f app-secret.yaml
secret/app-secret created

# To view the secret content, we need to retrieve the secret in YAML format
vagrant@controlplane:~$ kubectl get secret app-secret -o yaml
apiVersion: v1
data:
  api_key: YXNkZnc0MzVzZWYyMzQ1
  db.properties: dXNlcm5hbWU6IGRidXNlcgpwYXNzd29yZDogZGJwYXNzd29yZAo=
kind: Secret
metadata:
  annotations:
    kubectl.kubernetes.io/last-applied-configuration: |
      {"apiVersion":"v1","kind":"Secret","metadata":{"annotations":{},"name":"app-secret","namespace":"default"},"stringData":{"api_key":"asdfw435sef2345","db.properties":"username: dbuser\npassword: dbpassword\n"},"type":"Opaque"}
  creationTimestamp: "2026-07-26T11:40:12Z"
  name: app-secret
  namespace: default
  resourceVersion: "1307923"
  uid: 1ef1f5c7-9279-4449-ae0c-dd400c774e57
type: Opaque
```

The output, the secret data is presented in **base64** format.

Additionally, **stringData** is automatically converted to data in the output YAML because only the data field supports base64-encoded values.

```TEX
# decode the output using the base64 utility and check if we get the values used in the YAML
vagrant@controlplane:~$ echo "YXNkZnc0MzVzZWYyMzQ1" | base64 -d
asdfw435sef2345

# 
vagrant@controlplane:~$ echo "dXNlcm5hbWU6IGRidXNlcgpwYXNzd29yZDogZGJwYXNzd29yZAo=" | base64 -d
username: dbuser
password: dbpassword
```

### Creating a Secret With base64 Encoded Data

Using the data field instead of stringData allows you to create a secret, but you must manually encode the values with base64 encoding.

```bash
backend_api_key: 11235813
db_password: my3ecret

# we need to encode the values using base64 encoding
vagrant@controlplane:~$ echo -n "11235813" | base64
MTEyMzU4MTM=

vagrant@controlplane:~$ echo -n 'my3ecret' | base64
bXkzZWNyZXQ=
```

> The **-n** option in the echo command is used to prevent echo from appending a **newline character** (\n) at the end of the string it outputs.

Now we need to use the encoded values in the YAML manifest with the data field.

```bash
# Create backend-secret.yaml
apiVersion: v1
kind: Secret
metadata:
  name: backend-secret
type: Opaque
data:
  backend_api_key: MTEyMzU4MTM=
  db_password: bXkzZWNyZXQ=

# create the secret and check the secret data
vagrant@controlplane:~$ kubectl apply -f backend-secret.yaml
secret/backend-secret created
```


### Injecting Secrets into Pods

Injecting Secret data into pods can be done using:

1. **Environment Variables:** This method is straightforward and allows you to easily reference Secrets as environment variables within your application.
2. **Volume Mounts:** This method is more secure for handling sensitive data, as it avoids exposing secrets in the environment. It allows you to use secrets as files within your application.

We'll deploy a **MySQL** pod in K8s with its credentials and configuration securely managed using K8s Secrets. We'll achieve this by:

- Creating a Secret that stores MySQL credentials and a configuration file.
- Defining a MySQL pod that consumes these Secrets both as environment variables and as a mounted configuration file.

The official MySQL image supports values using the **MYSQL_USER**, **MYSQL_PASSWORD**, and **MYSQL_ROOT_PASSWORD** environment variables. We will inject these variables into the pod using secrets.

### Create MySQL Secret

First, we need to convert all values to base64 encoding because we will use the data field in the secret object.

```bash
vagrant@controlplane:~$ echo -n "mysqluser" | base64
bXlzcWx1c2Vy

vagrant@controlplane:~$ echo -n "mysqlpassword" | base64
bXlzcWxwYXNzd29yZA==

vagrant@controlplane:~$ echo -n "rootpassword" | base64
cm9vdHBhc3N3b3Jk

vagrant@controlplane:~$ echo -n "[client] user=admin password=admin" | base64
W2NsaWVudF0gdXNlcj1hZG1pbiBwYXNzd29yZD1hZG1pbg==
```

Now that we have the required base64 encoded values, let's create the secret object with all the values mapped to their respective keys.

```bash
apiVersion: v1
kind: Secret
metadata:
  name: mysql-secret
type: Opaque
data:
  mysql-user: bXlzcWx1c2Vy
  mysql-password: bXlzcWxwYXNzd29yZA==
  mysql-root-password: cm9vdHBhc3N3b3Jk
  mysql-config-file: W2NsaWVudF0KdXNlcj1hZG1pbgpwYXNzd29yZD1hZG1pbg==
```

```bash
# Create the secret
vagrant@controlplane:~$ kubectl apply -f mysql-secret.yaml
secret/mysql-secret created
```


### Create MySQL Pod With Secrets

```bash
# Create mysql.yaml
apiVersion: v1
kind: Pod
metadata:
  name: mysql-pod
spec:
  containers:
  - name: mysql
    image: mysql
    env:
    - name: MYSQL_USER
      valueFrom:
        secretKeyRef:
          name: mysql-secret
          key: mysql-user
    - name: MYSQL_PASSWORD
      valueFrom:
        secretKeyRef:
          name: mysql-secret
          key: mysql-password
    - name: MYSQL_ROOT_PASSWORD
      valueFrom:
        secretKeyRef:
          name: mysql-secret
          key: mysql-root-password
    volumeMounts:
    - name: mysql-secret-volume
      mountPath: /etc/mysql/conf.d
      readOnly: true
  volumes:
  - name: mysql-secret-volume
    secret:
      secretName: mysql-secret
```

In the above pod manifest, we consume three secret data as environment variables (MYSQL_USER, MYSQL_PASSWORD, and MYSQL_ROOT_PASSWORD) using the following fields.

```bash
valueFrom:
    secretKeyRef
```

And we consume the whole secret data as a volume using the secret type. All the secrets get mounted to **/etc/mysql/conf.d** path inside the container.

```bash
volumes:
  - name: mysql-secret-volume
    secret:
      secretName: mysql-secret
```

```bash
# deploy the MySQL pod
vagrant@controlplane:~$ kubectl apply -f mysql-pod.yaml
pod/mysql-pod created

# Ensure the MySQL pod is in running state


# Validate Secrets
# First, check if the environment variables have the updated secrets
vagrant@controlplane:~$ kubectl get pods
NAME                                            READY   STATUS    RESTARTS      AGE
mysql-pod                                       1/1     Running   0             3m42s

# check if the environment variables have the updated secrets
vagrant@controlplane:~$ kubectl exec -it mysql-pod -- printenv
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
HOSTNAME=mysql-pod
GOSU_VERSION=1.19
MYSQL_MAJOR=9.7
MYSQL_VERSION=9.7.1-1.el9
MYSQL_SHELL_VERSION=9.7.1-1.el9
MYSQL_USER=mysqluser
MYSQL_PASSWORD=mysqlpassword
MYSQL_ROOT_PASSWORD=rootpassword
MY_RELEASE_PROMETHEUS_ADAPTER_PORT_443_TCP_PROTO=tcp
```

From the output, you can see that the secrets are applied to the environment variables.

```bash
# Now, let's validate the secret volume
vagrant@controlplane:~$ kubectl exec -it mysql-pod -- ls /etc/mysql/conf.d

# Delete the secret and pod
vagrant@controlplane:~$ kubectl delete pod mysql-pod --force
```

### Secret Imperative Commands

For the **CKA exam**, you must know all the **imperative commands** to manage secrets.

```bash
# create a secret that holds a username and password
vagrant@controlplane:~$ kubectl create secret generic app-secret --from-literal=username=admin --from-literal=password=secret
secret/app-secret created
```

The **--from-literal** option is used to specify the key-value pairs in the command itself.

```golang
# You can directly decode the secret values using the JSON path
vagrant@controlplane:~$ kubectl get secret app-secret -o jsonpath='{.data.username}' | base64 -d
admin

vagrant@controlplane:~$ kubectl get secret app-secret -o jsonpath='{.data.password}' | base64 -d
secret
```

If we have more key-value pairs, we can use the **--from-file** option to specify a path to the file that contains the required data.

```bash
# Create a my-secrets.txt

password=supersecret
api-key=12345-abcde-67890-fghij

# create the secret using the text file
vagrant@controlplane:~$ kubectl create secret generic backend-secret --from-file=my-secrets.txt
secret/backend-secret created

# Verify the secret
vagrant@controlplane:~$ kubectl get secret backend-secret -o yaml
```

### Managing Secrets In Real World Setup

In real-world setups, particularly in enterprise environments, secrets are usually stored and managed using external secret management tools to comply with organizational security policies.

- HashiCorp Vault
- AWS Secrets Manager
- Google Cloud Secret Manager
- Azure Key Vault

These tools and services provide features like automatic password rotation and data encryption, enhancing security and ensuring compliance for organizations.

Secrets stored in these tools can be consumed as K8s secrets using the following tools:

- **External Secrets Operator:** This tool syncs secrets from external secret management systems (such as AWS Secrets Manager, HashiCorp Vault, and Google Cloud Secret Manager) into K8s secrets.
- **Secrets Store CSI Driver:** This driver allows pods to mount secrets, keys, and certificates from external secret management systems as volumes.
- **Sealed Secrets by Bitnami:** Encrypts K8s secrets so they can be safely stored in version control systems and can only be decrypted by the controller in the K8s cluster.
