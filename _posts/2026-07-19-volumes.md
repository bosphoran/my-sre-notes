## Introduction

When a pod is terminated or a container within a pod crashes, all the data stored within the container's filesystem is lost forever.

> To persist data in K8s, we use **volumes**. Volumes allow pods to store and share data across multiple containers within the pod.

Just like mounting a storage device in Linux or a cloud VM, you can mount a pod volume to a specific path within a container's filesystem.

- A volume could be an empty directory or a specific path inside the worker node's filesystem.
- It can be a single file.
- It could be external storage like an EBS volume attached to the node.
- It could be a Network File System (NFS) attached to the node.
- Or it could be a K8s object like ConfigMap or Secret.

The following image illustrates the relationship between the pod, the volume, and the few types of storage mount paths.

![Volumes]({{ site.baseurl }}/assets/img/k8s-course/volumes.jpg)

### Volume Types

- **EmptyDir:** The data is stored on the worker node's filesystem where the pod is running. Data in an EmptyDir volume is ephemeral and lasts only as long as the pod is running.
- **HostPath:** The data is stored in a specific directory on the worker node's filesystem.
- **PersistentVolume (PV):** The data is stored on external storage resources.
  - Cloud Block Storage: Services like AWS EBS, Google Cloud Persistent Disk, or Azure Disk.
  - Object Storage: Services like Amazon S3, Google Cloud Storage can be used as storage options.
  - Network File System (NFS): Data is stored on a network file system like AWS EFS.

```bash
apiVersion: v1
kind: Pod
metadata:
  name: simple-pod
spec:
  containers:
    - name: app
      image: nginx
      volumeMounts: # Mount the volume inside the container at /data
        - name: my-volume
          mountPath: /data
  volumes: # Define the volumes that can be mounted by containers in this Pod
    - name: my-volume
      # Create a temporary directory.
      # Data exists only while the Pod is running.
      emptyDir: {}
```

### emptyDir Volume

An emptyDir volume is a temporary storage volume that is created automatically when a Pod is scheduled to a node. It is initially empty and is deleted when the pod is removed from the node.

we can use **emptyDir** for a web server that processes data and caches intermediate results to improve performance. If the pod restarts, the cache can be rebuilt.

### Why we need emptyDir in K8s

> An **emptyDir** volume exists in K8s for one simple reason: Pods often need temporary scratch space, and K8s must provide a safe, isolated place for that data to live while the Pod is running.

Many applications need a place to write temporary files:

- caches
- logs
- buffers
- session data
- intermediate processing files

emptyDir gives the Pod a shared, writable directory that all containers inside the Pod can use.

### Creating emptyDir Volumes

> **emptyDir** is needed because Pods often require temporary, fast, shared, non-persistent storage.

A Deployment with a multi-container pod (two containers):

- A webserver container that uses the nginx image.
- A log-reader container that uses the busybox image.

The webserver container mounts the default nginx log files (**access.log** and **error.log**) to the pod's shared volume, **nginx-logs**, at **/var/log/nginx**. The volume is an emptyDir volume.

The **log-reader** container mounts the same shared volume at **/webserver-logs**, giving it access to the log files written by the webserver container. It then outputs the access and error logs to STDOUT using the tail command.

![Volumes 2]({{ site.baseurl }}/assets/img/k8s-course/volumes-2.jpg)

Here's the **webserver.yaml** file for the nginx deployment with a multi-container pod.

```bash
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-app
  template:
    metadata:
      labels:
        app: nginx-app
    spec:
      containers:
      - name: webserver
        image: nginx
        volumeMounts:
        - name: nginx-logs
          mountPath: /var/log/nginx
      - name: log-reader
        image: busybox
        command: ["/bin/sh", "-c", "tail -f /webserver-logs/access.log /webserver-logs/error.log"]
        volumeMounts:
        - name: nginx-logs
          mountPath: /webserver-logs
      volumes:
      - name: nginx-logs
        emptyDir: {}
```

1. In the above manifest, under the volumes spec, we declare a volume named nginx-logs of type emptyDir: {}.
2. Inside the container spec, we use the nginx-logs volume via volumeMounts, where the /var/log/nginx path of the webserver container is mounted to the empty directory.
3. The /webserver-logs path of the log-reader container is also mounted to the same volume.

```bash
# apply the deployment yaml

    Medium:
```


### Creating emptyDir Memory Backed Volumes

By default, **emptyDir** volumes are stored on the disk of the node. However, K8s also provides the option to create emptyDir volumes that are backed by node memory instead of disk storage.

When you create an **emptyDir** volume with the medium field set to Memory, K8s creates a tmpfs (temporary filesystem) mount backed by the node's memory. The data stored in this volume resides in memory and is not written to disk.

> **tmpfs** is a type of filesystem that uses the system’s RAM for storage, making it very fast compared to disk-based storage.

We'll create a Redis pod that uses an emptyDir volume backed by memory, mounting it to the Redis **/data** directory.

```bash
# Create a redis-emptydir.yaml.
apiVersion: v1
kind: Pod
metadata:
  name: redis-pod
spec:
  containers:
  - name: redis
    image: redis:latest
    ports:
    - containerPort: 6379
    volumeMounts:
    - name: redis-data
      mountPath: /data
  volumes:
  - name: redis-data
    emptyDir:
      medium: Memory
      sizeLimit: 500Mi
```

When specifying the **sizeLimit**, you can use different units of measurement, such as:

- Ki for kibibytes (1024 bytes)
- Mi for mebibytes (1024 kibibytes)
- Gi for gibibytes (1024 mebibytes)

```bash
vagrant@controlplane:~$ kubectl apply -f redis-emptydir.yaml
pod/redis-pod created

# verify pod status
vagrant@controlplane:~$ kubectl get pods
NAME                                            READY   STATUS    RESTARTS       AGE
redis-pod                                       1/1     Running   0              17s

# describe the pod to validate if the memory volume has been created
vagrant@controlplane:~$ kubectl describe pod redis | grep volume -B6
Volumes:

    Medium:     Memory
    SizeLimit:  500Mi

    Type:                    Projected (a volume that contains injected data from multiple sources)
```

### hostPath Volume

A **hostPath** volume allows a pod to access a specific directory or file on the worker node's filesystem.

```bash
volumes:
- name: host-storage
  hostPath:
    path: /var/log/app
```

It mounts this directory or files into the pod's filesystem, making it accessible to the containers within the pod.

> We can use hostPath when multiple pods on the same node need to share data. For example, a web server and a logging agent running on the same node share a hostPath volume to exchange log files.

![Volumes 3]({{ site.baseurl }}/assets/img/k8s-course/volumes-3.jpg)

### Creating hostPath Volume

```bash
volumes:
- name: nginx-logs
  hostPath:
    path: /var/log/nginx
    type: DirectoryOrCreate
```

Here, we have used the **type: DirectoryOrCreate** so that if the **/var/log/nginx** directory doesn't exist on the worker node, it will be created.

```bash
# Create hostdir.yaml 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 1
  selector:
    matchLabels:
      app: nginx-app
  template:
    metadata:
      labels:
        app: nginx-app
    spec:
      containers:
      - name: webserver
        image: nginx
        volumeMounts:
        - name: nginx-logs
          mountPath: /var/log/nginx
      - name: log-reader
        image: busybox
        command: ["/bin/sh", "-c", "tail -f /webserver-logs/access.log /webserver-logs/error.log"]
        volumeMounts:
        - name: nginx-logs
          mountPath: /webserver-logs
      volumes:
      - name: nginx-logs
        hostPath:
          path: /var/log/nginx
          type: DirectoryOrCreate
```

Here, both the **webserver** and **log-reader** containers refer to the same volume, which is the **/var/log/nginx** directory on the worker node where the pod is deployed.

```bash
# deploy the hostdir yaml
vagrant@controlplane:~$ kubectl apply -f hostdir.yaml
deployment.apps/nginx-deployment created

# Get the pod details.
vagrant@controlplane:~$ kubectl get pods
NAME                                            READY   STATUS    RESTARTS       AGE
nginx-deployment-7cb4d79f6d-x2m89               2/2     Running   0              34s

# Validate the volume mount
vagrant@controlplane:~$ kubectl describe po nginx-deployment-7cb4d79f6d-x2m89 | grep volume -B2
Volumes:
  nginx-logs:
    Type:          HostPath (bare host directory volume)
--
    HostPathType:  DirectoryOrCreate
  kube-api-access-t6pfx:
    Type:                    Projected (a volume that contains injected data from multiple sources)
```

Let's write a custom log to the **/var/log/nginx/access.log** file present in the webserver container.

```bash
vagrant@controlplane:~$ kubectl exec -it nginx-deployment-7cb4d79f6d-x2m89 -c webserver -- sh -c 'echo "Custom Log entry" >> /var/log/nginx/access.log'
```

Now, if you check the logs of the **log-reader** container, you should see the custom log entries that were written by the **webserver** container.


### Mount a file using hostPath

The **file mount** is useful in scenarios where a container needs to access specific configuration files or other data files present on the host system.

Let's look at an example where we mount the **/etc/kubernetes/kubelet.conf** file from the worker node (present on all worker nodes) into a pod using a hostPath volume.

```bash
# Create filepath.yaml
apiVersion: v1
kind: Pod
metadata:
  name: kubelet-conf-pod
spec:
  containers:
  - name: config-reader
    image: busybox
    command: ["sh", "-c", "cat /host/kubelet.conf && sleep 3600"]
    volumeMounts:
    - name: kubelet-config
      mountPath: /host/kubelet.conf
  volumes:
  - name: kubelet-config
    hostPath:
      path: /etc/kubernetes/kubelet.conf
      type: File
```

In this example, we create a volume using the type: File specification to mount the **/etc/kubernetes/kubelet.conf** file from the host system into the container. Inside the container, this file is accessed through the **/host/kubelet.conf** mount path.

In the container's command, we use cat to print the contents of the **/host/kubelet.conf** file, which will then appear in the Pod's logs.

```bash
# Deploy the pod and check the log to verify the file mount
vagrant@controlplane:~$ kubectl apply -f filepath.yaml
pod/kubelet-conf-pod created

# verify pod status
vagrant@controlplane:~$ kubectl get pods
NAME                                            READY   STATUS    RESTARTS       AGE
kubelet-conf-pod                                1/1     Running   0              19s

# 
vagrant@controlplane:~$ kubectl logs kubelet-conf-pod
apiVersion: v1
clusters:
- cluster:
    certificate-authority-data: LS0tLS1CRUdJTiBDR
# ...
```

As you can see, the pod logs show the content from the **kubelet.conf** file, confirming the file mount.

```bash
# Now, clean up the pod.
vagrant@controlplane:~$ kubectl delete pod kubelet-conf-pod
pod "kubelet-conf-pod" deleted from default namespace
```
