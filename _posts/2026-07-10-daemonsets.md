## Introduction

**DaemonSets** are used when you need a Pod running on every node to provide node-level functionality like logging, monitoring, or networking.

It guarantees that exactly one Pod, managed by the **DaemonSet**, runs on each worker node in the cluster.

![DaemonSets]({{ site.baseurl }}/assets/img/k8s-course/daemonset.jpg)

By specifying **nodeSelector**, **nodeAffinity**, **taints**, and **tolerations** pod properties in a DaemonSet definition, you can control which nodes the DaemonSet pods are scheduled on.

The **kube-proxy** component, responsible for service networking within the cluster, is typically deployed using a DaemonSet.

**Real-World Use Cases of DaemonSets:**

- **Cluster Log Collection:** To run log collector like Fluentd, Logstash, or Fluent Bit on every node to centralize Kubernetes logging data.
- **Cluster Monitoring:** To deploy monitoring agents, such as Prometheus Node Exporter, on each node in the cluster to collect and exposes node-level metrics.
- **Storage Provisioning:** To run a storage plugin on every node to provide a shared storage system to the entire cluster.
- **Network Management:** To deploy Network plugins or firewalls agents on all nodes (e.g., the Calico CNI plugin) to enforce consistent network policy enforcement across the cluster.

### Creating a Daemonset

To understand the use case of **DaemonSets**, let's consider a real-world example of centralized K8s logging using the **ELK** stack (Elasticsearch, Logstash, and Kibana).

![DaemonSets ELK]({{ site.baseurl }}/assets/img/k8s-course/daemonset-elk.jpg)

In K8s, the standard practice is to write application logs to the standard output (STDOUT) and standard error (STDERR) streams.

- On each worker node, there are multiple pods running applications. These pods generate logs that need to be collected and processed.
- A **daemonset** is used to deploy a log agent pod on each worker node. The daemonset ensures one **log agent pod** runs on every node. In this case, the log agent is **Fluentbit**.
- The **Fluentbit** log agent pod, deployed via the daemonset, mounts the log directories from the node (**/var/log/containers**, **/var/log/pods**) to access the logs generated by the application pods on that node.
- **Fluentbit** reads the logs from the mounted directories, collects them, and forwards them to the log **processor/forwarder**, which is **Logstash** in this architecture.
- **Logstash** receives the log data from **Fluentbit**, processes it (parsing, transforming, enriching), and then forwards the structured log data to **Elasticsearch** for storage and indexing.
- **Elasticsearch** stores and indexes the log data received from Logstash, making it searchable and analyzable.
- **Kibana**, the visualization component, connects to **Elasticsearch** to retrieve the indexed log data and provides an interface for searching, visualizing, and dashboarding the log data.

### Deploy a Fluentd Daemonset

Create a **daemonset.yaml** file and copy the following contents. It is minimal configuration that deploys a basic **Fluentd DaemonSet** on all worker nodes in your cluster:

```bash
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: fluentd
  labels:
    app: fluentd-logging
spec:
  selector:
    matchLabels:
      app: fluentd-logging
  template:
    metadata:
      labels:
        app: fluentd-logging
    spec:
      containers:
      - name: fluentd
        image: fluentd:latest
```

Let’s deploy this manifest.

```bash
vagrant@controlplane:~$ kubectl apply -f daemonset.yaml
daemonset.apps/fluentd created

# Check the DaemonSet status
vagrant@controlplane:~$ kubectl get daemonset
NAME      DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
fluentd   2         2         2       2            2           <none>          56s

# Check the pod status
vagrant@controlplane:~$ kubectl get pods -o wide
NAME                            READY   STATUS    RESTARTS       AGE    IP               NODE     NOMINATED NODE   READINESS GATES
fluentd-b994j                   1/1     Running   0              112s   10.244.196.143   node01   <none>           <none>
fluentd-gkkm4                   1/1     Running   0              111s   10.244.140.88    node02   <none>           <none>
```

You can see fluentd pods are running on the two available worker nodes.

```bash
# Describe: Get detailed information about the DaemonSet
vagrant@controlplane:~$ kubectl describe daemonset fluentd

# Edit: Modify the DaemonSet configuration
vagrant@controlplane:~$ kubectl edit daemonset fluentd

# Clean up the daemonset.
vagrant@controlplane:~$ kubectl delete daemonset fluentd
daemonset.apps "fluentd" deleted from default namespace
```

### Scenario 01: Deploy Monitoring Agent as Daemonset

- Create a **DaemonSet** to deploy the **Prometheus Node Exporter** across all nodes in the cluster. The Node Exporter image to use is **prom/node-exporter:v1.7.0**.
- The DaemonSet should be named **prometheus-node-exporter**.
- Deploy the **DaemonSet** in the **monitoring namespace**. Create the namespace if it does not exist.
- Create a YAML manifest named **node-exporter.yaml** and deploy the Prometheus Node Exporter as a DaemonSet, addressing all the above objectives.

```bash
# Create the monitoring namespace
vagrant@controlplane:~$ kubectl create ns monitoring
namespace/monitoring created

# Create the node-exporter.yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: prometheus-node-exporter
  namespace: monitoring
  labels:
    app: prometheus-node-exporter
spec:
  selector:
    matchLabels:
      app: prometheus-node-exporter
  template:
    metadata:
      labels:
        app: prometheus-node-exporter
    spec:
      containers:
      - name: node-exporter
        image: prom/node-exporter:v1.7.0

# Now apply this manifest
vagrant@controlplane:~$ kubectl apply -f node-exporter.yaml
daemonset.apps/prometheus-node-exporter created

# Validate the DaemonSet status
vagrant@controlplane:~$ kubectl get ds -n monitoring
NAME                       DESIRED   CURRENT   READY   UP-TO-DATE   AVAILABLE   NODE SELECTOR   AGE
prometheus-node-exporter   2         2         2       2            2           <none>          35s

# Check if it has successfully scheduled node exporter pods on all worker nodes.
vagrant@controlplane:~$ kubectl get pods -o wide -n monitoring
NAME                             READY   STATUS    RESTARTS   AGE   IP               NODE     NOMINATED NODE   READINESS GATES
prometheus-node-exporter-cq8wv   1/1     Running   0          69s   10.244.140.92    node02   <none>           <none>
prometheus-node-exporter-vfv9b   1/1     Running   0          69s   10.244.196.144   node01   <none>           <none>
```
