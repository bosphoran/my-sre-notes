## Introduction

When you deploy a frontend application in K8s, it needs to be accessible from outside the cluster to allow end users to interact with it. This access can be configured as either private (restricted access) or public (open access).

Similarly, if you have backend application pods, they must expose a single endpoint that allows the frontend application pods to communicate with them.

Also, backend application pods may need to connect to database pods, which also require a properly configured endpoint.

![Services]({{ site.baseurl }}/assets/img/k8s-course/services.jpg)

### Challenges With Pod IPs

Using pod IP addresses to expose your applications just doesn't work well.

- **Ephemeral Nature of Pods:** Pods are ephemeral, meaning they can be created, destroyed, or rescheduled based on the cluster's needs.
- **Dynamic IP Addresses:** When pods are recreated, they often get new IP addresses, making it unreliable to use pod IPs for communication.
- **Scalability and High Availability:** Multiple instances of a pod may be running, managed by higher-level resources like Deployments to ensure high availability and scalability.

K8s **Services** provide stable IP to a set of pods.

---

### Static IP Address & DNS

A Service keeps a fixed IP address and DNS, even as the pods it manages are created and destroyed. The IP and DNS remain constant for the service's lifetime.

Let's say you have a web application running in multiple pods. The Service gives a consistent IP address and DNS name to the web app. So even if some pods go down or new ones are created, users can always reach the web app at the same address.

![Services 2]({{ site.baseurl }}/assets/img/k8s-course/services-2.jpg)

### Load Balancing

Services automatically balance the load, spreading traffic across all the pods they manage.

> **Kube-proxy** acts as the network proxy on each node, ensuring that client requests hitting a Service are correctly routed to the appropriate Pods.

By default, Kube-proxy uses iptables mode, which sends traffic to backend pods randomly for each new connection (basic form of load balancing).

### Routing Traffic to Pods

Services use label selectors to determine which pods to target.

When you create a Service, you define a selector that matches the labels assigned to the pods. The Service then routes traffic to the pods that have those matching labels.

![Services 3]({{ site.baseurl }}/assets/img/k8s-course/services-3.jpg)

One key thing to remember is, when a Service defines multiple labels in its selector, it uses an AND logical operator between these labels.

It means a Pod must match ALL the labels specified in the service label selector to be selected by the Service. Here is an illustration for the same.

![Services 4]({{ site.baseurl }}/assets/img/k8s-course/services-4.jpg)

### Types of Services

- **ClusterIP Service:** It exposes the Service on an internal IP from the cluster service CIDR. It is primarily used for internal application to application connectivity.
- **NodePort Service:** This type exposes the Service on each Node's IP at a static port. (ports 30000-32767)
- **LoadBalancer Service:** This type creates an external load balancer in cloud providers and exposes the Service externally. For example, in AWS EKS it creates an Application Load Balancer (ALB).
- **ExternalName Service:** This type maps the Service to a DNS name, acting as an alias for an external service. So, the traffic flow is essentially in the opposite direction compared to a LoadBalancer or NodePort. Meaning the ExternalName service forwards internal K8s traffic out of the cluster to an external DNS name.

### Exposing Deployment Using Service

To expose a deployment using the service we can use the **kubectl expose** command

```bash
vagrant@controlplane:~$ kubectl expose deploy nginx-webserver --name=nginx-service --port=80 --target-port=80
service/nginx-service exposed
```

- **port:** This is the port exposed by the Service itself. It’s the stable, external-facing port that clients use to connect to the Service.
- **targetPort:** This is the port on the actual Pods (containers) that the Service forwards traffic to. It maps the Service’s port to the container’s port.

And here is the YAML alternative for the same expose command.

```bash
apiVersion: v1
kind: Service
metadata:
  name: nginx-service
spec:
  selector:
    app: nginx-webserver
  ports:
    - port: 80
      targetPort: 80
```

> Service keeps track of its target pods using the **EndpointSlices API**. EndpointSlices are objects that store the IP addresses and ports of the Pods that are selected by a Service.

- The EndpointSlice controller continuously monitors the Pods that match the Service.
- As Pods are created, become ready, or are removed, the controller updates the appropriate EndpointSlice or creates a new EndpointSlice as needed.
- Now, the Kube Proxy running on each node watches the EndpointSlices for updates. It ensures that network traffic is correctly routed to the appropriate pod endpoints by observing these slices.
- When a Pod is added, removed, or changes status, Kube-proxy updates the node’s networking rules based on the information in the EndpointSlice.

### DNS Based Service Discovery

Imagine you have servers that can be created or destroyed at any moment—relying on their IP addresses would be a nightmare because those IPs could change at any time.

Instead of keeping track of IP addresses, clients typically use a static DNS endpoint or query a service registry to find the available backend servers. This makes it much easier to connect to the right services without worrying about where they are currently running.

> Service discovery is a method of identifying and accessing devices and services automatically on a network. It is a common pattern followed in distributed systems and microservice architectures.

Pods in K8s don’t have fixed IPs, so using them directly isn’t reliable.
Instead of tracking Service IPs manually, K8s simplifies this with DNS-based service discovery. You just call the Service by name, and K8s automatically routes your request to the right Pods.

### Kubernetes DNS Server

K8s runs a DNS server internally. It allows pods and services to locate and communicate with each other using domain names instead of IP addresses. 

K8s typically uses **CoreDNS** as its DNS server, and it runs in the kube-system namespace.

```bash
vagrant@controlplane:~$ kubectl get pods -n kube-system

coredns-66bc5c9577-tf5wj               1/1     Running   22 (25h ago)     55d
```

### Service DNS

When a service is created, it automatically gets a DNS entry. For example, we have created the service **nginx-service** in the default namespace. So it gets the DNS name **nginx-service.default.svc.cluster.local**(fully qualified domain name (FQDN).

The DNS system within K8s automatically constructs this URL based on the service name, namespace, and the cluster domain.

### Pod resolv.conf File

So, how does a pod actually resolve the DNS for a service? This is where the **resolv.conf** file inside the pod comes into play.

> The resolv.conf file is a configuration file used in Unix and Unix-like operating systems, including Linux. Its main job is to set up the system's DNS resolver, which is responsible for translating domain names into IP addresses. Essentially, it tells the system where to find the DNS servers needed to perform this translation.

In K8s, the Kubelet writes the DNS settings to the pod's /etc/resolv.conf file. By the time the pod is up and running, this file is already set up and ready to handle DNS queries.

Let's take a look at **/etc/resolv.conf** file from within a pod.

```bash
vagrant@controlplane:~$ kubectl run test-pod --rm -it --image=busybox -- /bin/sh
All commands and output from this session will be recorded in container logs, including credentials and sensitive information passed through the command prompt.
If you don't see a command prompt, try pressing enter.
/ # cat /etc/resolv.conf
search default.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5
/ # exit
Session ended, resume using 'kubectl attach test-pod -c test-pod -i -t' command when the pod is running
pod "test-pod" deleted from default namespace
```

As you can see from the output, there's a **nameserver 10.96.0.10** entry, which points to the **CoreDNS** service endpoint. This means that all DNS queries from the pod are directed to the CoreDNS server, where they are resolved to the corresponding Service IP addresses.

### How Does NodePort Work

When you create a NodePort service, K8s allocates a port from a range (default is 30000-32767) on all the nodes in your cluster, unless you specify a particular port.

When you create a **NodePort** service, the K8s API server notifies the **kube-proxy** component on each node about the service and its associated **EndpointSlice** objects (which contain the details of the pods selected by the service)

**kube-proxy** then writes the necessary rules to **iptables** (or IPVS) on each node to ensure that traffic directed to the NodePort is properly routed to one of the corresponding pods.

When a request hits the NodePort, here is what happens.

- When traffic hits any node's IP on the NodePort. The node's kube-proxy intercepts this traffic (Interception happens at the network level - OSI Layer 4 - Transport layer).
- kube-proxy references the pre-configured (IPTables Or IPVS) rules to determine the corresponding service.
- The service's EndpointSlice maintains a list of endpoints (IPs of the pods that match the service's selector).
- kube-proxy uses this information to choose a pod.
- If there are multiple pods, kube-proxy performs load balancing to distribute traffic among them.
- kube-proxy then uses NAT (Network Address Translation) to forward the traffic to the chosen pod's IP and port.
- The pod processes the request and sends a response.
- Before the response is sent back to the client, kube-proxy performs reverse NAT. This involves modifying the source IP and port in the response packet to match the original Node IP and NodePort.

### Kube Proxy Load Balancing

**kube-proxy** manages **load balancing** behind the scenes, focusing on a specific feature within iptables known as **statistic mode random probability**.

> Statistic mode random probability is a feature of iptables that allows you to match a specific percentage of network packets randomly. This feature is often used for packet filtering and network address translation (NAT) but can also be applied to distribute traffic across multiple pods in a K8s deployment.

### Load Balancer Service

The issue with using a NodePort service is that relying on Node IPs to expose an application is problematic because nodes in K8s clusters are ephemeral. This makes NodePort a potential single point of failure.

To address this, K8s offers a service type called **LoadBalancer**. When you create a Service of type **LoadBalancer**, K8s provisions a load balancer on the corresponding cloud platform.

When running K8s on the cloud, the cluster needs to interact with various cloud services, such as load balancers, storage, and IAM services. The **cloud controller manager** component is responsible for integrating the cluster with the respective cloud services.

For instance, when you create a **LoadBalancer service**, the API server communicates with the **cloud controller manager** to provision the corresponding load balancer on the cloud platform.

### LoadBalancer Provisioning Workflow

When you create a LoadBalancer type service in K8s, it does the following.

1. Internally, K8s first creates a **ClusterIP service**.
2. On top of the ClusterIP service, K8s creates a **NodePort service**. This exposes the service on a specific port on all nodes in the cluster. (eg: 32000)
3. K8s communicates with the **Cloud Controller Manager** component to create the Load Balancer.
4. The Cloud Controller Manager makes API calls to the cloud provider to request the provisioning of an external load balancer (e.g., AWS ELB, Google Cloud Load Balancer).
5. The cloud provider provisions an external load balancer (e.g., AWS ELB, Google Cloud Load Balancer)
6. Now, the Load Balancer adds all the worker nodes in the cluster as its target to route the traffic to the port assigned by the NodePort. This allows the cloud load balancer to send traffic to any node in the cluster.

### LoadBalancer To Service Traffic Workflow

1. A client (user/service) sends a request to the external IP address or DNS provided by the cloud load balancer.
2. The cloud load balancer receives the request. It selects a node from the Kubernetes cluster (usually round-robin or least connections).
3. The request is then forwarded to the selected node on the NodePort opened by the NodePort service.
4. Once the traffic reaches a node, kube-proxy (which runs on every node) takes over. It uses iptables rules (or IPVS rules, depending on the configuration) to route the traffic to the appropriate pod.
5. The selected pod processes the request and sends a response. The response follows the reverse path back to the client.

### Creating a Load Balancer Service

To create a LoadBalancer type service, simply set the **type field to LoadBalancer** in your service definition (type: LoadBalancer).

```bash
apiVersion: v1
kind: Service
metadata:
  name: frontend-service
  namespace: default
  labels:
    app: frontend-app
spec:
  type: LoadBalancer
  selector:
    app: frontend-app
  ports:
    - protocol: TCP
      port: 80            
      targetPort: 8080
```

Here is the equivalent imperative command.

```bash
vagrant@controlplane:~$ kubectl expose deployment frontend-app --name=frontend-service --namespace=default --type=LoadBalancer --port=80 --target-port=8080 --protocol=TCP --labels=app=frontend-app
```

### MetalLB Summary

**MetalLB** is a **network load balancer** implementation for K8s clusters in on-premises or bare metal environments. It functions as a software load balancer, enabling the testing of Load Balancer services and practical learning of ingress in Kubeadm clusters.

**To set up MetalLB:**

- Install MetalLB by using the provided manifest and verify pod status.
- Define a range of IP addresses for LoadBalancer Services within the K8s node network.
- Create a config map in the metallb-system namespace with the IP range.
- Deploy MetalLB in Layer 2 mode using a configuration file.

After configuring MetalLB, you can test LoadBalancer Services by exposing a deployment as a LoadBalancer, assigning an external IP from the MetalLB range, and accessing the service.

**Key points about how MetalLB works:**

- MetalLB assigns an IP from the configured pool for LoadBalancer services.
- In enterprise environments, network administrators would typically assign the IP pool.
- The assigned IP acts as a virtual IP (VIP) managed by MetalLB without being tied to a specific NIC.
- Nodes in the cluster take ownership of the VIP through leader election by MetalLB speaker pods.

In Layer 2 mode, traffic is directed to a single node holding the VIP, which then routes it to the appropriate pods through K8s service networking. However, there are drawbacks to consider:

- Traffic funnels through a single node, limiting bandwidth and functioning more as failover than load balancing.
- Supports failover with delay, potentially causing brief service interruptions during node transitions.

### Externalname Service

An ExternalName service in K8s acts like a DNS alias. Instead of exposing a ClusterIP or routing traffic inside the cluster, it simply maps the service name to an external DNS name.

- It works like a CNAME record within the cluster.
- Traffic is forwarded out of the cluster to the external service.
- No ClusterIP is created — it’s purely for DNS resolution, not for internal load balancing.

> ExternalName lets you call external services using a K8s service name, but it doesn’t provide an internal endpoint.

Suppose we need to connect to the external website google.com using an ExternalName service.

```bash
# create a file named externalname.yaml
apiVersion: v1
kind: Service
metadata:
  name: search # Sets the name of the service to search. This name is used within the cluster to refer to the service.
spec:
  type: ExternalName # Specifies that this is an ExternalName service.
  externalName: google.com # Indicates the external DNS name to which the service maps.
                           # When a pod in the cluster queries the search service, it will be resolved to google.com
```

```bash
# create the service
vagrant@controlplane:~$ kubectl apply -f xternalname.yaml
service/search created

# get the service details
vagrant@controlplane:~$ kubectl get svc search
NAME     TYPE           CLUSTER-IP   EXTERNAL-IP   PORT(S)   AGE
search   ExternalName   <none>       google.com    <none>    58s
# you can see that the EXTERNAL-IP points to google.com
```

When using an ExternalName service in K8s, the traffic flow is as follows

![Services 12]({{ site.baseurl }}/assets/img/k8s-course/services-12.jpg)

- Pod queries CoreDNS using service name.
- CoreDNS resolves it to the external DNS name.
- Pod sends a request to the resolved external DNS name.
- External Service handles the request and responds.
- Response is sent back to the Pod.

### Real World Example

Let's say you are working on an application migration where you plan to move all workloads to K8s and migrate the **PostgreSQL** database to a cloud-managed solution like Amazon RDS.

Currently, the database is running on a self-managed server with the hostname **db.techiescamp.com**. Your goal is to migrate the database without causing downtime or requiring significant code changes in the application.

To achieve this, you can use an **ExternalName** service in K8s.

1. Create a **ExternalName** service named **app-db** pointing to **db.techiescamp.com**.
2. Configure the application to use the **app-db** service endpoint for database connections, and then deploy the application on K8s.
3. Create the new **RDS** instance with the hostname **techiescamp-db.123456.us-east-1.rds.amazonaws.com** and perform the data migration to the new RDS instance.
4. Once you're ready for the switch over, update the **ExternalName** service app-db to point to the new RDS endpoint.
5. The application continues to use **app-db** as the database hostname. If any issues occur, you can quickly revert to the old database by simply changing the **ExternalName** service back to the original endpoint.

- {SVCNAME}_SERVICE_HOST: The host IP address of the service.
